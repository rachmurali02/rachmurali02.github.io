Deep Dive into Text Chunking Strategies

Chunking is the unsung hero of RAG systems. After weeks of experimentation, here's what I learned about splitting text the right way.

Last week, I shared my experiments with RAG systems. This week, I'm zooming in on what turned out to be one of the most critical — yet overlooked — components: text chunking. The way you split documents can make or break your entire retrieval pipeline.

Why Chunking is Harder Than It Looks

At first glance, chunking seems trivial. Just split text into pieces, right? But after building several RAG systems, I realized that chunking decisions cascade through your entire pipeline:

  • Too small: Chunks lose context, leading to incomplete or misleading retrievals
  • Too large: Retrieval becomes noisy, and you waste precious context window space
  • Poor boundaries: Splitting mid-sentence or mid-thought breaks semantic coherence
  • No overlap: Important context at chunk boundaries gets lost

The challenge is that there's no one-size-fits-all solution. The optimal strategy depends on your documents, your queries, and your LLM's context window.

Four Strategies I Tested

Strategy 1: Fixed-Size Chunking

The simplest approach: split text every N characters or tokens. This is what most tutorials start with. 

def chunk_fixed_size(text, chunk_size=512):
    chunks = []
    for i in range(0, len(text), chunk_size):
        chunks.append(text[i:i + chunk_size])
    return chunks

✅ Pros

  • Dead simple to implement
  • Predictable chunk sizes
  • Works well with token limits
  • Fast processing

❌ Cons

  • Splits mid-sentence, mid-word, mid-thought
  • No respect for semantic boundaries
  • Can create incoherent fragments
  • Poor performance on structured documents

My verdict: Good for quick prototypes, but rarely optimal for production. I saw retrieval quality improve 20-30% just by switching to smarter strategies.

Strategy 2: Sentence-Based Chunking

Split on sentence boundaries, then group sentences until you hit your target size. This preserves semantic units. 

def chunk_by_sentence(text, target_size=512):
    sentences = sent_tokenize(text)
    chunks = []
    current_chunk = []
    current_size = 0
    
    for sent in sentences:
        sent_size = len(sent)
        if current_size + sent_size > target_size and current_chunk:
            chunks.append(' '.join(current_chunk))
            current_chunk = []
            current_size = 0
        current_chunk.append(sent)
        current_size += sent_size
    
    if current_chunk:
        chunks.append(' '.join(current_chunk))
    return chunks

✅ Pros

  • Respects natural language boundaries
  • Each chunk is coherent and readable
  • Works well for narrative text
  • Better retrieval quality than fixed-size

❌ Cons

  • Variable chunk sizes (some very small, some very large)
  • Sentence detection isn't perfect (abbreviations, etc.)
  • Still loses context at boundaries
  • Doesn't handle lists, code, or structured content well

My verdict: Solid middle ground. I used this for most of my experiments with narrative documents. The variable chunk sizes can be mitigated with min/max constraints.

Strategy 3: Sliding Window with Overlap

This is where things get interesting. Instead of clean cuts, we create overlapping windows. Each chunk shares some context with its neighbors. 

def chunk_sliding_window(text, size=512, overlap=50):
    chunks = []
    step = size - overlap
    
    for i in range(0, len(text), step):
        chunk = text[i:i + size]
        if len(chunk) < overlap:  # Skip tiny end chunks
            break
        chunks.append(chunk)
    
    return chunks

✅ Pros

  • Preserves context across boundaries
  • Catches information that spans chunk borders
  • More forgiving of arbitrary splits
  • Improved recall in retrieval

❌ Cons

  • Increases storage and compute (more chunks)
  • Redundant information in the database
  • Can retrieve near-duplicate chunks
  • Overlap size is another hyperparameter to tune

My verdict: The overlap is crucial for high-quality RAG. I settled on 10-20% overlap as a sweet spot. Yes, it increases costs, but the retrieval quality improvement is worth it.

Strategy 4: Semantic/Paragraph Chunking

Split on natural document structure: paragraphs, sections, or semantic boundaries. This is my favorite for well-structured documents. 

def chunk_by_paragraph(text):
    paragraphs = text.split('\n\n')
    chunks = []
    current_chunk = []
    current_size = 0
    target_size = 512
    
    for para in paragraphs:
        para = para.strip()
        if not para:
            continue
        para_size = len(para)
        
        if para_size > target_size:
            if current_chunk:
                chunks.append('\n\n'.join(current_chunk))
                current_chunk = []
                current_size = 0
            chunks.append(para)
        elif current_size + para_size > target_size:
            if current_chunk:
                chunks.append('\n\n'.join(current_chunk))
            current_chunk = [para]
            current_size = para_size
        else:
            current_chunk.append(para)
            current_size += para_size
    
    if current_chunk:
        chunks.append('\n\n'.join(current_chunk))
    return chunks

✅ Pros

  • Respects document structure and hierarchy
  • Each chunk is a complete thought or topic
  • Best user experience (readable, coherent chunks)
  • Works beautifully for blog posts, papers, documentation

❌ Cons

  • Highly variable chunk sizes
  • Some chunks can be very large (requires splitting)
  • Depends on document formatting
  • Doesn't work for unstructured text

My verdict: When it works, it's magical. I use this for technical documentation, blog posts, and papers. For messy or unformatted text, fall back to sentence-based chunking.

Real-World Performance Comparison

I tested all four strategies on a corpus of 100 technical documents with 500 test queries. Here's what I found:

Strategy Retrieval Precision Avg Chunk Size Total Chunks
Fixed Size 62% 512 1,247
Sentence-Based 74% 487 1,309
Sliding Window 79% 512 1,556
Paragraph 82% 521 1,198

Paragraph chunking won by a significant margin, with 82% retrieval precision. But here's the interesting part: when I combined paragraph chunking with 15% overlap, precision jumped to 86%.

Lessons Learned & Best Practices

💡 Start with Document Structure

If your documents have clear structure (paragraphs, sections, headings), use that as your primary chunking signal. Fall back to sentence-based for edge cases.

💡 Overlap is Worth the Cost

10-20% overlap dramatically improves retrieval quality. Yes, you'll store more chunks, but modern vector databases are cheap. Retrieval quality is expensive.

💡 Chunk Size Depends on Context

For GPT-4 with 128k context, I use 512-1024 token chunks. For smaller models, 256-512 is safer. Always measure retrieval quality, not just arbitrary sizes.

💡 Add Metadata to Chunks

Store document title, section headings, and position metadata with each chunk. This helps with re-ranking and lets you filter retrievals.

Advanced Techniques I'm Exploring

Hierarchical Chunking

Instead of flat chunks, create a hierarchy: document → section → paragraph → sentence. Retrieve at the paragraph level, but include parent section context. Early results show 12% improvement in complex queries.

Semantic Chunking with LLMs

Use a small LLM to identify topic boundaries: "Where does the topic change?" This is slower and more expensive, but produces semantically coherent chunks even in unstructured text.

Adaptive Chunking

Different documents need different strategies. I'm building a classifier that picks the best chunking strategy per document based on structure, content type, and formatting.

Wrapping Up

Chunking might seem like a boring preprocessing step, but it's actually one of the highest-leverage optimizations you can make in a RAG system. Here's my recommended approach:

  1. Start with paragraph/semantic chunking if your documents have structure
  2. Add 10-20% overlap to preserve boundary context
  3. Set min/max constraints (e.g., 200-1000 tokens) to avoid extremes
  4. Include rich metadata (title, section, position) with each chunk
  5. Measure retrieval quality on real queries, not synthetic tests
  6. Iterate based on failure cases — look at bad retrievals and adjust
